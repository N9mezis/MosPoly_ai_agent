# Перенос интерфейса ViWork в MosPoly AI Agent

Базой для дальнейшей работы служит React-приложение этого репозитория.
Из MVP `contract-checker` (коммит `626eef1`) перенесены визуальный стиль,
типографика, логотип, навигация, область загрузки с выбранным
файлом, сводка и фильтры отчёта, оформление нормативной базы. Во время
ожидания запросов и индексации интерфейс показывает Busy. Анимация отключается
при системной настройке уменьшения движения.

На странице проверки тип договора выбирается из выпадающего списка.
Данные о типах и их доступности приходят из API. Карточки на старом прототипе
Figma показывают предыдущий вариант выбора.

HTML-шаблоны Python, отдельный preview, скрипты Figma и экспортные артефакты
MVP здесь не нужны. Служебные скрипты запуска, тестирования и миграции
этого репозитория остаются на месте.

## Интеграция

- `frontend/src` — React/TypeScript, общий дизайн в `styles.css`,
  элементы загрузки и Busy в `ui.tsx`. Шрифт и его лицензия — в `assets/`.
- Используется существующий клиент `/api/v1`. При загрузке сначала
  `POST /documents` возвращает ID файла, затем `POST /analyses` создаёт
  задачу. Статус опрашивается каждые 1,5 с, а готовый отчёт загружается
  отдельно. Выгрузку PDF/DOCX формирует бэкенд.
- JWT, права, история, подсветка договора, пользователи и управление
  нормативкой остаются частью приложения. JSON для нормативной базы
  ограничен 5 МиБ; новая версия сначала индексируется в воркере, затем
  её можно активировать. Лимит договора по умолчанию — 10 МиБ.
- FastAPI, PostgreSQL с pgvector, Redis и ARQ остаются источником данных
  и выполнения анализа. Старые SQLite, векторы в памяти и API MVP
  не используются новым интерфейсом. Логика RAG не менялась.

Запуск: `make up` или инструкции в README. В mock-режиме можно проверить
весь путь через настоящий API, БД и воркер без ключей и без вызова внешней LLM.

## Задачи дорожной карты

| Задача | Реализация |
|---|---|
| Э6-01 | Сводка фильтрует замечания одним нажатием; сортировка по важности или номерам пунктов; переход между карточкой и цитатой с переносом фокуса. |
| Э6-02 | Очередь, извлечение, проверка пунктов, прогресс, ориентир по выполненным пунктам, отмена с подтверждением, частичный результат и технические сбои отдельно. |
| Э6-03 | Подсказки по кодам загрузки, обработки и доступа. При сбое создания повтор использует тот же ID документа и ключ запроса. |
| Э6-04 | Сценарий и форма для пяти участников готовы. Проверка с людьми и отчёт ещё не проведены. |
| Э8-01 | Карточка нормы открывает полный сохранённый фрагмент использованной редакции, даты и ссылку источника, если они есть. Цитата остаётся видна отдельно. |
| Э8-02 | Сервер сравнивает сохранённый фрагмент с активной версией того же источника. Если текст отличается или фрагмент не найден, видны пометки в отчёте и истории. Смена даты без смены текста не считается изменением нормы. |
| Э8-03 | По номеру можно открыть сохранённый отчёт и посмотреть доступный снимок версии, моделей и отпечатков промптов. Это не новый запуск. Воспроизведение конвейера не реализовано: исходный файл удаляется, а API запуска по снимку отсутствует. |
| Э2-01–04, интерфейс | [Набор сценариев, фикстуры и инструкция](../frontend/tests/README.md). Chrome и Firefox проверяются в CI; браузерные тесты используют тестовые ответы, отдельно API-тесты проверяют БД. |

Порядок ревью: сначала перенос `b/v2-frontend-integration` в `main`,
затем `b/v2-frontend-roadmap`. До первого слияния diff второй ветки
сравнивать с `b/v2-frontend-integration`, чтобы не видеть перенос повторно.

Отдельные направления бэкенда и данных — наборы и регрессия качества,
сравнение моделей, обновление нормативки и сокращение ложных замечаний.
Расширение типов документов зависит от готовности профилей и данных.
Опубликованные замеры относятся к синтетической выборке и не означают,
что продукт прошёл приёмку.

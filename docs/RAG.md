# Конвейер проверки и поиск норм (RAG)

## Поток одной проверки

```
POST /documents ──► валидация (формат, размер, пустой/битый файл) ──► временный файл в томе uploads
POST /analyses  ──► analyses(queued) ──► Redis/ARQ ──► worker: analyze
worker:
  1. извлечение текста DOCX/PDF  → исходный файл удаляется сразу (НФ-04)
  2. классификатор: не трудовой договор → failed / not_employment_contract (Ф-12)
  3. обезличивание блоков (ФИО, паспорт, СНИЛС, ИНН, телефоны, email, адрес проживания)
  4. чанкирование по пунктам (3.1, 3.2 …), блоки сохраняют block_id для подсветки
  5. снимок нормативки: активные версии источников профиля (фиксируются на всю проверку)
  6. проверка полноты всего договора (ст. 57, 100): правила + LLM
  7. по каждому пункту, параллельно (LLM_MAX_PARALLEL):
       правила (ст. 91, 115, 136, 70) → гибридный поиск → LLM → проверка цитат
  8. дедупликация, категории, подсветка → findings, retrievals, llm_calls, summary
```

Если LLM недоступна, пункты получают технический статус `error`, замечания правил сохраняются,
проверка помечается `is_partial=true`: частичный результат лучше полного отказа.

## Нормативная база

- Источник (`regulation_sources`, например `tk_rf`) → **неизменяемые версии** (`regulation_versions`) → фрагменты (`regulation_chunks`: статья, часть, заголовок, текст, эмбеддинг, `tsvector`).
- Загрузка: `POST /api/v1/regulations` (JSON, формат — `data/regulations/source.example.json`) или `python -m app.cli import-kb`. Фрагменты длиннее 1500 символов делятся по предложениям.
- Индексация в воркере: эмбеддинг считается **один раз** по тексту с контекстным заголовком «ТК РФ, ст. 91 «…», ч. 2: …». Кеш `embedding_cache(model, sha256)` не даёт платить за один и тот же текст дважды.
- Активация — одна транзакция: прежняя активная версия источника уходит в архив. Откат = активация архивной версии.
- Колонка `vector` без фиксированной размерности: у моделей `Embeddings` и `EmbeddingsGigaR` размерности разные. При смене модели — `python -m app.cli reindex`. Поиск сравнивает только векторы той же размерности. HNSW-индекс добавим, если база вырастет до 10⁵ фрагментов; сейчас точный перебор занимает миллисекунды.

## Гибридный поиск (`app/knowledge/retrieval.py`)

| Канал | Как работает | Что ловит |
|---|---|---|
| dense | `embedding <=> query` (pgvector, косинус), top-20 | синонимы и перефразирование |
| lexical | `to_tsquery('russian', 'слово1 \| слово2 \| …')`, `ts_rank_cd`, top-20 | точные юридические формулировки |
| hints | явные «ст. 91» в тексте + словарь «тема → статьи» из профиля (`check_profiles.params.article_hints`) | гарантирует ключевые статьи |

Важно: `websearch_to_tsquery` соединяет слова через AND и по длинному пункту почти ничего не находит, поэтому строится OR-запрос, а стемминг и стоп-слова отдаются PostgreSQL.

Слияние — RRF (k = 60) → кандидаты (12) → реранкер → top-k (4) в LLM. Ранги и скоры каждого канала сохраняются в `retrievals`: по ним видно, ошибся ли поиск (нужной нормы нет в выдаче) или модель (норма была, а замечания нет).

## Реранкер (`app/knowledge/rerank.py`, `RERANKER=none|gigachat|http`)

- `none` (по умолчанию) — порядок RRF;
- `gigachat` — listwise: один вызов LLM на пункт, кандидаты оцениваются по шкале 0–3, строгая `json_schema`; используется ключ LLM и модель `GIGACHAT_RERANK_MODEL`. При ошибке — мягкий откат к RRF;
- `http` — любой сервис `/rerank` в формате Jina/Cohere/TEI (`RERANK_HTTP_URL`), например bge-reranker на машине с GPU.

Включать реранкер стоит только если `evaluate-retrieval --rerank` показывает выигрыш: на маленькой базе он лишь добавляет вызовы.

## Оценка качества

```bash
python -m app.cli evaluate-retrieval [--rerank]   # recall@1/3/5 и MRR по каналам (Ф-04)
python -m app.cli evaluate --rules-only           # точность/полнота без LLM
python -m app.cli evaluate                        # полный прогон с текущей LLM
```

Результаты пишутся в `eval_runs` (с коммитом и конфигурацией) и в `evals/results*`.

Текущие цифры (hashing-эмбеддинги, 14 фрагментов, 31 размеченный пункт):

| конфигурация | recall@1 | recall@3 | recall@5 | MRR |
|---|---|---|---|---|
| dense | 0.581 | 0.839 | 0.935 | 0.731 |
| lexical | 0.548 | 0.935 | 0.968 | 0.750 |
| hints | 0.613 | 0.613 | 0.742 | 0.645 |
| **hybrid** | **0.774** | **0.968** | **1.000** | **0.879** |

Rules-only на 20 договорах: precision 0.541, recall 0.645 (совпадает с MVP). Полный прогон с GigaChat ещё не делался: нужны ключи.

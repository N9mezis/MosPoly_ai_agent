# Проверка трудовых договоров по ТК РФ

ИИ-агент загружает трудовой договор (DOCX/PDF), обезличивает его, находит применимые нормы ТК РФ (гибридный поиск по базе знаний), проверяет пункты правилами и языковой моделью (GigaChat) и формирует отчёт: замечания с цитатами из договора и нормы, категорией и рекомендацией.

Стек: Python 3.12, FastAPI, SQLAlchemy, PostgreSQL 16 + pgvector, Redis + ARQ, React + Vite, Docker Compose. Модели вызываются только по API, локального инференса нет.

Интерфейс поддерживает загрузку, просмотр статуса и истории проверок, отчёт с подсветкой и выгрузку в PDF и DOCX. План — [docs/PLAN.md](docs/PLAN.md), контракты — [docs/CONTRACTS.md](docs/CONTRACTS.md), устройство поиска — [docs/RAG.md](docs/RAG.md).

## Быстрый старт

Нужен [Docker Desktop](https://www.docker.com/products/docker-desktop/) (Windows/macOS) или Docker Engine + Compose (Linux).

**Windows (PowerShell):**

```powershell
git clone https://github.com/N9mezis/MosPoly_ai_agent.git
cd MosPoly_ai_agent
.\scripts\up.ps1
```

**Linux / macOS / WSL:**

```bash
git clone https://github.com/N9mezis/MosPoly_ai_agent.git && cd MosPoly_ai_agent && make up
```

Затем откройте:

- интерфейс — http://localhost:8080
- документация API (Swagger) — http://localhost:8000/docs
- готовность сервисов — http://localhost:8000/readyz

По умолчанию `LLM_PROVIDER=mock` и `EMBEDDING_PROVIDER=hashing`: всё работает без ключей и без обращения к внешним сервисам.

Для первой проверки загрузите любой DOCX из `data/contracts/problematic/`. API при старте применяет миграции, создаёт демо-пользователя и загружает нормативную базу, если она пуста. Если анализ не стартует, проверьте состояние API и воркера командой `docker compose ps` и посмотрите логи через `docker compose logs api worker`.

### Вход и режим разработки

В локальном `.env` по умолчанию включён `AUTH_DEV_MODE=true`: API выполняет запросы от имени демо-администратора. Для проверки настоящего входа до первого запуска задайте в `.env` `AUTH_DEV_MODE=false`, случайный `JWT_SECRET` длиной от 32 байт и свой `SEED_ADMIN_PASSWORD`. Для входа используйте `SEED_ADMIN_EMAIL` и заданный пароль. Если база уже создана, используется сохранённый в ней пароль.

Фронтенд хранит access-токен в памяти, а refresh-токен в `localStorage`, чтобы восстанавливать сессию после обновления страницы. Хранение refresh-токена в `localStorage` — компромисс учебного проекта.

## Подключение моделей

**LLM — GigaChat.** В [личном кабинете](https://developers.sber.ru/studio) создайте проект GigaChat API и скопируйте **Client ID** и **Client Secret**:

```dotenv
LLM_PROVIDER=gigachat
GIGACHAT_CLIENT_ID=...
GIGACHAT_CLIENT_SECRET=...
GIGACHAT_LLM_SCOPE=GIGACHAT_API_PERS
GIGACHAT_LLM_MODEL=GigaChat-2
# freemium допускает один одновременный запрос, иначе ответы 429
LLM_MAX_PARALLEL=1
```

Authorization key собирается из этой пары автоматически; готовый ключ можно передать напрямую в `GIGACHAT_LLM_CREDENTIALS`.

**Эмбеддинги — Cloud.ru Foundation Models** (OpenAI-совместимый API). Создайте сервисный аккаунт в проекте, затем API-ключ с доступом к Foundation Models:

```dotenv
EMBEDDING_PROVIDER=openai_compatible
EMBEDDING_BASE_URL=https://foundation-models.api.cloud.ru/v1
EMBEDDING_API_KEY=...
EMBEDDING_MODEL=Qwen/Qwen3-Embedding-0.6B
```

Можно и через GigaChat (`EMBEDDING_PROVIDER=gigachat`), но на freemium-аккаунте эмбеддинги отвечают 402. Без ключей используется офлайн-режим `EMBEDDING_PROVIDER=hashing`.

**Реранкер** (`RERANKER`): `none` — порядок гибридного поиска (по умолчанию); `http` — Cloud.ru `BAAI/bge-reranker-v2-m3` (`RERANK_HTTP_URL=https://foundation-models.api.cloud.ru/v1/rerank`, `RERANK_HTTP_FORMAT=cohere`, ключ — `RERANK_HTTP_API_KEY`; нужен баланс на счёте); `gigachat` — реранкинг через GigaChat тем же ключом. Подробнее — [docs/RAG.md](docs/RAG.md).

После смены настроек:

```bash
docker compose up -d                                                  # перезапуск с новым .env
docker compose run --rm api python -m app.cli check-gigachat --smoke  # доступ к GigaChat
docker compose run --rm api python -m app.cli reindex                 # эмбеддинги нормативки под новую модель
```

Сертификат НУЦ Минцифры уже лежит в `certs/` и подключается автоматически. Ключи хранятся только в `.env`, который не попадает в Git.

### Результаты замера

**Проверка замечаний — 20 размеченных договоров, 31 ожидаемое замечание:**

| Конфигурация | Precision | Recall | Выдано / совпало | Время на договор | Токены GigaChat |
|---|---|---|---|---|---|
| только правила (без LLM) | **0.541** | 0.645 | 37 / 20 | < 1 с | 0 |
| правила + GigaChat-2 + поиск на Qwen3 | 0.205 | **0.806** | 122 / 25 | ~35 с | ~14 тыс. (284 тыс. на 20) |
| цель ТЗ (НФТ-4) | ≥ 0.85 | ≥ 0.80 | | ≤ 60 с (НФ-01) | |

Как читать эти цифры:
- **LLM поднимает полноту** с 0.645 до 0.806, то есть до уровня цели ТЗ. Прирост (+5 совпадений) — на договорах с явными нарушениями (кейсы 02, 03, 05), где модель добирает то, что не поймали правила. На кейсах 06–10 с «естественными» и замаскированными формулировками («период адаптации 120 дней», «составной график») и правила, и LLM находят лишь 1 из 7. Пропущено 6 из 31: ст. 57 — 3, ст. 91, 136, 70 — по одному.
- **Но точность низкая.** На 10 корректных договорах — 53 ложных замечания, ни один корректный договор не прошёл «чистым». Ложные замечания по статьям: ст. 57 — 37, ст. 67 — 11, ст. 72 — 10, ст. 136 — 9, ст. 108 — 6. Из 97 лишних 80 — замечания LLM по отдельным пунктам: модель трактует как нарушение законные или нейтральные формулировки («работа не имеет разъездного характера», «заработная плата 20-го и 5-го числа»). Ещё 17 — предупреждения правил полноты (см. следующий пункт).
- **Технические сбои — 27.** 20 из них — проверка полноты договора целиком (ст. 57, 100): на длинном контексте GigaChat-2 в режиме строгой `json_schema` возвращал пустой ответ, и конвейер откатывался на regex-правила. **Исправлено после замера**: на пустой ответ запрос повторяется без схемы. Цифры выше сняты до исправления, перезамер — следующий шаг. Остальные 7 — сбои проверки отдельных пунктов.
- **Время.** ~35 с на договор при `LLM_MAX_PARALLEL=1` (ограничение freemium) — в пределах НФ-01; в интерфейсе выходит 60–80 с за счёт очереди и сохранения результата.

**Поиск норм — 31 запрос (пункт договора → ожидаемая статья), 1868 фрагментов ТК:**

| Конфигурация | recall@1 | recall@3 | recall@5 | MRR | recall@3* |
|---|---|---|---|---|---|
| только векторы (Qwen3-Embedding-0.6B) | 0.581 | 0.613 | 0.710 | 0.626 | 0.857 |
| только BM25 | 0.290 | 0.516 | 0.548 | 0.409 | 0.619 |
| только подсказки по статьям | 0.613 | 0.742 | 0.742 | 0.677 | 0.905 |
| **гибрид (используется)** | **0.710** | **0.774** | **0.774** | **0.752** | **0.952** |

`recall@3*` — только по статьям, которые конвейер ищет поиском (21 запрос). Цель Ф-04 (нужная статья в top-3 ≥ 85 %) по ним выполнена. Для сравнения: с офлайн-эмбеддингами (hashing) гибрид давал recall@3 = 0.742.

**Итог первой версии:** поиск норм и полнота выявления — на уровне целей ТЗ; точность замечаний (0.21 против ≥ 0.85) — главный нерешённый вопрос. Приёмочным критериям продукт пока не соответствует.


### Как считались метрики

**Данные.** `data/contracts/` — 40 синтетических трудовых договоров, сгенерированных скриптами исходного MVP (contract-checker): 20 корректных и 20 с намеренно внесёнными нарушениями. Имена и реквизиты вымышлены. Разметка ожидаемых замечаний (`evals/demo_cases.json`) есть **только для 20 из них** — `correct_01–10` и `problematic_01–10`; кейсы 11–20 ещё не размечены. Всего в разметке 31 ожидаемое замечание: ст. 57 — 9, ст. 91 — 6, ст. 136 — 6, ст. 115 — 5, ст. 70 — 4, ст. 100 — 1. Разметку делала команда; юридическую экспертизу, которую требует ТЗ (п. 9.1), она не проходила.

**Проверка замечаний** (`python -m app.cli evaluate`). Каждый договор прогоняется через тот же конвейер, что и в интерфейсе. Выданное замечание засчитывается как совпадение, если совпадают **три поля**: номер пункта договора (`3.2` или `document` для отсутствующего условия), номер статьи ТК и допустимый статус (`violation` или `warning`). Одно ожидаемое замечание может совпасть только с одним выданным.
- **precision** = совпавшие / все выданные (видимые) замечания;
- **recall** = совпавшие / все ожидаемые замечания;
- технические сбои (пункт не проверен из-за ошибки модели) в замечания не входят и считаются отдельно.

Правило строгое: замечание по верной статье, но привязанное к соседнему пункту, или верное по сути замечание со ссылкой на другую статью считается и промахом, и ложным срабатыванием.

**Проверка поиска** (`python -m app.cli evaluate-retrieval`). Для каждого ожидаемого замечания с конкретным пунктом (31 запрос) берётся обезличенный текст пункта, и проверяется, на какой позиции поиск выдаёт нужную статью: recall@1/3/5 и MRR. Отдельно считается **recall@3\*** — только по статьям, которые конвейер действительно ищет поиском (21 запрос). Ст. 57 и 100 подаются в проверку полноты договора напрямую, по номеру статьи (ТЗ, п. 5), поэтому от поиска не зависят.

Все прогоны сохраняются в таблицу `eval_runs` (конфигурация, модели, коммит, метрики, промахи), отчёты по договорам — в `evals/results*/`.

### Ограничения замера

- **Синтетика.** Договоры сгенерированы по шаблонам, нарушения внесены явно («45 часов», «отпуск 14 дней»). На реальных договорах формулировки разнообразнее, и цифры будут другими — скорее хуже.
- **Маленькая выборка.** 31 ожидаемое замечание: одно совпадение меняет recall на ~3 п. п. Доверительные интервалы широкие, сравнивать конфигурации с разницей в пару процентов нельзя.
- **Подгонка.** Веса поиска, подсказки по статьям и часть правил валидации настраивались на этой же выборке. Нужна отложенная часть — кейсы 11–20 после разметки.
- **Разметка не экспертная.** Часть «ложных срабатываний» может оказаться спорными, но допустимыми замечаниями, и наоборот.
- **Freemium GigaChat.** Ограничение на одновременные запросы (`LLM_MAX_PARALLEL=1`) делает проверку медленной; на платном тарифе параллельность и время будут другими.
- **Только 6 статей проверяются целенаправленно.** Замечания по другим статьям ТК возможны, но в разметке их нет: такие замечания попадают в «ложные срабатывания», даже если они верны.

2. Снизить ложные срабатывания LLM: промпты под GigaChat, примеры корректных формулировок, сравнение GigaChat-2 / 2-Pro / 2-Max на всей выборке (ТЗ, п. 7.1.1).

5. Ускорить проверку: параллельные вызовы на платном тарифе, кеш результатов.


## Частые проблемы

- **Порт занят** — поменяйте `WEB_PORT` / `API_PORT` / `DB_PORT` в `.env`.
- **`CERTIFICATE_VERIFY_FAILED` при обращении к GigaChat** — проверьте, что `certs/russian_trusted_root_ca_pem.crt` на месте; не отключайте проверку TLS.
- **Скрипты `.sh` падают с `\r`** — клон с CRLF; образ сам исправляет окончания строк, но лучше включить `git config core.autocrlf input`.
- **Контейнер остановился с кодом 137** — проверьте `docker compose ps -a` и логи. Если процесс завершён из-за нехватки памяти, увеличьте доступную Docker Desktop память и повторите запуск.

Результаты носят рекомендательный характер и не являются юридическим заключением.
